# Audit round 2: 2026-11-17

This audit checked the code at commit 3c8c0913, with migrations up to 0144 applied live. It covered security and bugs.

The audit ran in three passes:

1. **First audit.** Five read-only Codex audits ran in parallel, one per area: training (A), nutrition and forms (B), money and access (C), chat and KO (D), and points and public pages (E).
2. **Cross-check.** A different Codex account reviewed each area's findings and tried to disprove them.
3. **Owner-side check.** Claude re-read the code for the top findings and checked the live database read-only: policies, function definitions, bucket limits, and live row counts.

Result: all 15 findings held up. 12 were confirmed as described, and 3 were confirmed but narrower than first described (B-2, E-1, and A-1's practical reach). The audit found nothing that lets a stranger read another team's data. The two security items are narrow, and neither has a live case today.

Some severities differ from the Codex ratings. Those differences are explained in the table notes below.

## Security

| ID | Severity | What happens | Live today |
|---|---|---|---|
| B-1 | HIGH | A former captain can still read the assessment answers they collected before the player moved to another captain. They can also edit their old review or reply. The `form_requests_read`, `form_answers_read` and `form_requests_review` policies check only the stored captain id, not the current relationship. Other player data already closes on transfer (0113, `captain_since`), but forms do not. | 0 requests from former captains |
| A-1 | MEDIUM (Codex: CRITICAL) | A player can add a set log that points at any exercise id. That log then unlocks reading that exercise if it is an orphan (a private exercise left behind by a deleted captain). The cause is that `sync_set_logs` and the set_logs RLS never check whether the player may use the exercise. The reach is low: the attacker needs the exact UUID, and only the exercise name and notes are exposed. | 0 orphaned exercises |
| B-2 | MEDIUM (partial) | A frozen or expired player can still submit assessment answers by calling the server action directly. The normal app screen blocks this. The database answer guard checks the relationship but not `player_can_write()`. | — |

## Bugs

| ID | Severity | What happens |
|---|---|---|
| C-1 | HIGH (money) | A payment receipt sent without a renewal request is meant to pay off existing debt (0138 assumes this). Instead, accepting it forces the captain to enter days, renews the subscription, and records a new sale, while the old debt stays owed. Cause: `review_payment_receipt` always calls `renew_player_offer`. There are no such receipts live yet. |
| A-2 | MEDIUM | A player finishes a workout on phone A, then opens it on phone B. Phone B shows the first set as not done. Pressing "complete set" does nothing, and the finish screen never appears. Cause: hydration downloads the session but not its sets. |
| B-3 | MEDIUM | A captain deletes a question that a player already answered, then saves the form. The save always fails with a generic error. Cause: the answers' foreign key blocks deleting the question. |
| B-4 | MEDIUM | A captain edits a meal (for example, 100 g of rice becomes 200 g) after the player already logged it. The player's eaten totals change after the fact. Cause: meal logs store no snapshot of what was eaten. |
| B-5 | MEDIUM | A form photo between 5 and 10 MB passes the app check but is always rejected by storage, because the bucket limit is 5 MB. The player is stuck on a required photo question. |
| C-2 | MEDIUM | An invite with a future start date gives access right away. The player can log workouts before the start date. |
| D-1 | MEDIUM | On the captain dashboard, weekly adherence for rotating programs is wrong. For example, one workout done out of three scheduled shows 100%. |
| D-2 | MEDIUM | After a player moves to a new captain, the old captain's voice notes and replies show in the new captain's chat as if the new captain sent them. Only the player sees this, not the new captain. |
| D-3 | MEDIUM | Older voice messages in an open chat stop playing after one hour, because their signed links expire and are never renewed. |
| E-1 | MEDIUM (partial) | A one-week (non-repeating) plan keeps counting planned days for the rest of the month on the leaderboard. This lowers the player's adherence and position. |
| E-2 | MEDIUM | The public coach page "workouts logged" total includes workouts the player did with previous captains. |
| E-3 | MEDIUM | The public coach page shows 0% adherence for teams on rotating programs. |
